System

현장 기록, 가상 공장, 분석을 한 줄의 데이터로 잇습니다

설비가 멈추면 남는 기록은 하나입니다. 날짜, 설비번호, 정지 사유, 증상, 조치, 비가동 시간, 처리 상태. 현장 웹앱과 게임이 이 형식 하나를 같이 쓰기 때문에, 게임을 계속 업데이트해도 대시보드와 시트는 바꿀 필요가 없습니다.

1 · 기록한다

현장 웹앱은 사람이 입력한 비가동 이력을, 게임은 라인이 멈출 때마다 같은 형식의 이력을 남깁니다.

2 · 본다

대시보드는 게임 공장을 0.15초마다 읽어 라인 상태, 버퍼 재고, 가용률·성능·품질로 나눈 OEE를 보여 줍니다.

3 · 실험한다

게임과 같은 규칙의 모델로 수백 일을 돌려 버퍼 크기, 고장 간격, 복구 시간이 생산량에 주는 영향을 잽니다.

Model Validation

시뮬레이션을 믿기 전에, 시뮬레이션부터 검증했습니다

모델을 게임 코드와 한 줄씩 맞춰 보는 과정에서 실제 라인과 다르게 움직이는 지점 두 곳을 찾았습니다. 게임으로는 자연스럽지만, 디지털 트윈으로 쓰려면 고쳐야 하는 부분입니다.

발견 1 · 빈 자리 당김

앞 공장이 멈춰도 완성차 생산이 거의 줄지 않는다

앞 공장이 멈춰 뒤 공장 입구가 비면, 게임은 다음 차를 빈 자리만큼 앞으로 옮겨 넣습니다. 그래서 빈 자리가 라인 끝까지 흘러가지 않고, 버퍼 크기를 바꿔도 생산량이 변하지 않습니다. 실제 컨베이어에서는 빈 행거가 그대로 흘러가 출구에서 손실로 나타납니다.

// game.js · simLines()
- const d0 = last ? Math.max(0, last.d - GAP) : 0;
+ const d0 = (i === 0 && last) ? Math.max(0, last.d - GAP) : 0;

수정 전후 차이는 실험 1·2에 나와 있습니다.

발견 2 · 시간 간격 의존성

배속을 올리면 하루 생산량이 줄어든다

게임은 한 걸음에 최대 2분씩 시간을 넘깁니다. 차가 64px 간격을 10px/분으로 움직이니 이론 간격은 6.4분인데, 한 걸음이 1분이면 7걸음(7분)이 걸립니다. 배속이 높을수록 한 걸음이 커져 택트가 늘어나고, 대시보드의 성능 P가 떨어집니다.

// game.js · advance()
- const s = Math.min(dt, 2);
+ const s = Math.min(dt, 0.2);   // 64px ÷ (10px/분 × 0.2분) = 정확히 32걸음

모델로 잰 하루 생산: 계산 중입니다.

Field Data

현장 비가동 기록 웹앱도 같은 지표로 다시 만들었습니다

처음 만든 웹앱은 이력을 시트에 쌓는 데까지는 됐지만, 대시보드 숫자 일부가 코드에 고정돼 있었습니다. 게임과 같은 OEE 계산을 쓰도록 고치고, 게임 기록도 받을 수 있게 했습니다.

바꾼 것

  • 가동률고정값 92.5% 대신, 계획 가동시간에서 비가동 시간을 빼서 계산합니다.
  • OEE가용률 × 성능 × 품질로 나눠 보여 줘서 어느 쪽 손실인지 바로 보입니다.
  • 설비 목록고정 배열 대신 시트에 들어온 설비 번호로 만듭니다. 새 설비가 바로 보입니다.
  • 공장 도면미해결 이력이 있는 라인은 도면에서도 정지로 바뀝니다.
  • API?api=dashboard로 JSON을 주고, doPost로 게임 기록을 받습니다.
